Bảo mật Microservice và đăng nhập cho React SPA

Từ bức tranh tổng thể đến hai cách đăng nhập phổ biến: SPA tự giữ token (Authorization Code + PKCE) và BFF (Gateway giữ phiên). Có sẵn phòng thí nghiệm PKCE chạy ngay trong trang và demo từng bước với Spring.

1. Bài toán bảo mật trong Microservice

Trong monolith (ứng dụng nguyên khối), bạn chỉ có một cửa vào để bảo vệ. Với microservice, mỗi service là một chương trình riêng, nói chuyện với nhau qua mạng. Số "cửa" tăng lên, và mỗi lời gọi đi qua mạng đều là một chỗ có thể bị nghe lén hoặc giả mạo.

Mọi quyết định bảo mật đều xoay quanh ba câu hỏi:

  1. Xác thực (AuthN): người hoặc service đang gọi là ai?
  2. Phân quyền (AuthZ): danh tính đó được phép làm gì?
  3. Bảo vệ đường truyền và dữ liệu: nội dung có bị đọc hoặc sửa giữa chừng không? (mã hóa bằng TLS)
Hai loại "người gọi" cần phân biệt

Người dùng cuối (có trình duyệt, đăng nhập bằng mật khẩu) và service gọi service (máy với máy, không có người). Hai loại này dùng cơ chế khác nhau, và câu hỏi "SPA đăng nhập kiểu A hay B" chỉ nói về loại thứ nhất.

2. Các hướng tiếp cận

Không có một đáp án duy nhất. Thực tế các hệ thống kết hợp nhiều lớp. Bảng sau liệt kê các hướng chính theo thứ tự tiến hóa.

Với ứng dụng có giao diện web, thực tế hay gặp tổ hợp:hướng 3 + 4 cho tầng API, thêm hướng 5 khi hạ tầng đủ trưởng thành. Còn câu hỏi "trình duyệt đăng nhập thế nào và token nằm ở đâu" thu gọn thành hai kiến trúc:

Cách A: SPA là public client

Trình duyệt tự chạy Authorization Code + PKCE,giữ token trong JavaScript và gửi Authorization: Bearer ... tới Gateway. Gateway là Resource Server, không giữ phiên.

Cách B: BFF

Gateway đóng vai BFF: tự đăng nhập với Authorization Server,giữ token phía server. Trình duyệt chỉ có cookie phiên. Gateway gắn token khi chuyển request xuống service.

Phần 3 và 4 giải thích nền tảng. Phần 5 và 6 đi vào hai mô hình kiến trúc. Từ phần 8, tài liệu chuyển sang thực hành với Keycloak và Google Provider, sau đó là BFF.

Resource Server kiểm tra token mà không cần hỏi AS mỗi lần:

  1. Lần đầu, tải JWKS (danh sách khóa công khai) từ AS và cache lại.
  2. Kiểm tra chữ ký bằng khóa công khai: token có thật do AS ký, chưa bị sửa.
  3. Kiểm tra iss đúng AS tin cậy,exp chưa hết hạn,aud/scope phù hợp.

Trong Spring chỉ cần khai báo issuer-uri; Spring tự tìm JWKS qua địa chỉ /.well-known/openid-configuration.

3.2 Public client và confidential client

  • Confidential client (client bí mật): chạy ở nơi giấu được bí mật, ví dụ server. Có client_secret để chứng minh danh tính với AS. Gateway trong cách B là confidential client.
  • Public client (client công khai): chạy ở nơi ai cũng đọc được mã, như trình duyệt hoặc app di động.Không thể giấu secret(mở DevTools là thấy). SPA trong cách A là public client, nên không có client_secret, và PKCE ra đời để bù vào chỗ thiếu này.

3.3 Authorization Code Flow: phân biệt Front-channel và Back-channel

Authorization Code Flow là quy trình trong đó Client trước hết yêu cầu Authorization Server xác thực người dùng và cấp một authorization code. Sau đó Client dùng code này để yêu cầu token. Điểm quan trọng về mặt bảo mật là hai bước này không diễn ra trên cùng một kênh.

KênhĐặc điểmDữ liệu đi quaRủi ro cần kiểm soát
Front-channelLà kênh trao đổi thông qua trình duyệt của người dùng. Client chuyển hướng trình duyệt đến Authorization Server; sau khi đăng nhập, Authorization Server chuyển hướng trình duyệt trở lại Client và gửi authorization code trong URL callback.
Ví dụ: trình duyệt truy cập /authorize, sau đó quay về /callback?code=...&state=....		Authorization request, authorization code,state.URL có thể xuất hiện trong lịch sử, log, extension hoặc một số ngữ cảnh Referer.
Back-channel Là kênh trao đổi trực tiếp giữa Client và Authorization Server thông qua HTTPS. Client gửi authorization code cùng code_verifier đến token endpoint để đổi lấy token.
Ví dụ: ứng dụng gửi yêu cầu POST đến /token; token được trả về trong response, không cần đưa vào URL chuyển hướng. 		Authorization code,code_verifier, sau đó nhận token.Cần bảo vệ endpoint, TLS và cơ chế xác thực Client phù hợp.

Ta có thể đọc quy trình theo 6 bước:

  1. Client tạo request tới /authorize và chuyển trình duyệt sang Authorization Server.
  2. Authorization Server xác thực người dùng và xử lý consent nếu cần.
  3. Authorization Server redirect trình duyệt về redirect_uri, kèm code và state.
  4. Client nhận code và kiểm tra state trước khi tiếp tục.
  5. Client gọi /token qua HTTPS để đổi code lấy token. Với PKCE, request này còn phải chứa code_verifier.
  6. Authorization Server kiểm tra code, PKCE và các điều kiện liên quan rồi trả access token; nếu dùng OIDC, có thể trả thêm ID token.
Điểm cần ghi nhớ

Authorization code là mã trung gian, ngắn hạn và dùng một lần.Access token là credential dùng để gọi Resource Server. Vì vậy, việc code xuất hiện trên URL không đồng nghĩa token xuất hiện trên URL. PKCE bổ sung một điều kiện: kẻ cầm được code nhưng không có code_verifier sẽ không đổi được code thành token.

4. PKCE chi tiết

PKCE=Proof Key for Code Exchange("pixy"), chuẩn RFC 7636. Một câu: mỗi lần đăng nhập, Client tự tạo một bí mật dùng một lần, và phải show ra đúng bí mật đó khi đổi code lấy token.

4.1 Vấn đề cần giải quyết

Authorization code đi qua front-channel (URL). Giả sử kẻ xấu lấy được code đó (qua extension độc hại, log, hoặc trên mobile là app khác đăng ký cùng đường dẫn redirect). Kẻ xấu mang code tới /token để đổi lấy access token.

Confidential client thì không sợ chuyện này, vì đổi code phải kèm client_secret. Nhưng SPA là public client, không có secret, nên AS không phân biệt được "đúng ứng dụng đã xin code" với "kẻ cầm trộm code".

4.2 Ví dụ dễ hình dung: gửi áo khoác

Bạn đến nhà hàng, gửi áo khoác ở quầy.

  1. Bạn viết một dòng bí mật lên mẩu giấy và giữ trong túi (đây là code_verifier).
  2. Bạn đưa lễ tân dấu vân tay của mẩu giấy (đây là code_challenge). Từ dấu vân tay không thể dựng lại nội dung mẩu giấy (hàm băm một chiều).
  3. Lễ tân đưa bạn phiếu số 57 (đây là authorization code) và ghi lại "phiếu 57 gắn với dấu vân tay này".
  4. Giữa đường, một kẻ nhặt được phiếu 57 (code bị chặn). Hắn đến quầy đòi áo.
  5. Lễ tân yêu cầu: "Cho xem mẩu giấy gốc". Lễ tân lấy dấu vân tay mẩu giấy đó, so với bản đã ghi. Kẻ trộm không có mẩu giấy nên không lấy được áo. Bạn có mẩu giấy gốc nên nhận áo (đây là access token).

Phiếu số lộ ra không sao, vì nó vô dụng nếu thiếu mẩu giấy. Và mẩu giấy gốc chỉ được đưa ra ở bước cuối, qua back-channel.

4.3 Cơ chế từng bước

  1. SPA tự sinh code_verifier

    Chuỗi ngẫu nhiên 43 đến 128 ký tự (dùng CSPRNG). SPA giữ lại, không gửi đi đâu.

  2. SPA tính code_challenge

    code_challenge = BASE64URL( SHA-256( code_verifier ) ). Đây là phương thức S256.

  3. SPA đến Auth Server qua front-channel

    Chuyển hướng trình duyệt tới /authorize?...&code_challenge=...&code_challenge_method=S256. Chỉ có challenge đi trên URL, verifier thì không.

  4. Auth Server lưu challenge

    Người dùng đăng nhập xong, AS sinh authorization code và ghi nhớ code này đi cùng challenge.

  5. Auth Server đến SPA qua front-channel

    Redirect về redirect_uri?code=...&state=.... Đây là chỗ code có thể bị lộ.

  6. SPA đến Auth Server qua back-channel

    POST /token với grant_type=authorization_code,code,redirect_uri,client_id và code_verifier(bản gốc).

  7. Auth Server kiểm tra

    Tính BASE64URL(SHA-256(code_verifier)) rồi so với challenge đã lưu.Khớp thì phát access token (và ID token, refresh token).Không khớp thì trả lỗi invalid_grant.

4.4 Vì sao an toàn

  • Hàm băm một chiều: kẻ nghe lén thấy challenge ở bước 3 cũng không suy ra được verifier.
  • Verifier chỉ lộ ở bước 6, qua kết nối TLS tới AS, lúc đó code đã nằm trong tay SPA thật.
  • Dùng một lần: mỗi lần đăng nhập sinh cặp mới, bắt được cặp cũ vô ích.
  • Entropy cao: 32 byte ngẫu nhiên cho ra 43 ký tự, không thể đoán.

4.5 Chi tiết kỹ thuật cần biết

  • BASE64URL: Base64 thường có ký tự +,/,= làm hỏng URL. BASE64URL đổi + thành -,/ thành _ và bỏ = ở cuối.
  • S256 và plain:plain gửi thẳng verifier làm challenge, tức là mất tác dụng chống nghe lén. Chỉ dùng plain khi hoàn toàn không thể băm. Luôn chọn S256.
  • PKCE và client secret không loại trừ nhau. OAuth 2.1 (bản chuẩn hóa gộp các thực hành tốt) yêu cầu dùng PKCE cho mọi client, kể cả confidential client.
  • Implicit flow(trả token thẳng trên URL) đã bị loại khỏi khuyến nghị hiện nay; Authorization Code + PKCE thay thế nó cho SPA.

4.6 Phòng thí nghiệm PKCE

Phần này chạy thật trong trình duyệt bằng Web Crypto, đúng thuật toán mà thư viện OIDC dùng. Bấm lần lượt từng bước.

4.7 PKCE chống được gì, không chống được gì

Chống được

  • Đánh cắp hoặc chặn authorization code rồi đem đi đổi token.
  • Tiêm một code của kẻ tấn công vào phiên của nạn nhân (authorization code injection).

Không chống được

  • XSS: nếu kẻ tấn công chạy được JavaScript trong trang, hắn đọc thẳng token đã nhận xong.
  • Người dùng bị lừa nhập mật khẩu vào trang giả.
  • Thiết bị đã bị cài mã độc.

Dòng thứ nhất trong cột "không chống được" là lý do cách B tồn tại. Xem phần 5 và 6.

5.2 Luồng đầy đủ

  1. SPA đến Auth Server

    Tạo verifier, challenge và state; chuyển hướng tới /authorize.

  2. Auth Server đăng nhập người dùng

    Form đăng nhập nằm trên domain của AS, SPA không bao giờ thấy mật khẩu.

  3. Auth Server đến SPA

    Redirect về SPA kèm code và state. SPA kiểm tra state khớp.

  4. SPA đến Auth Server(/token)

    Gửi code +code_verifier. Nhận access token, ID token, (có thể) refresh token.

  5. SPA đến Gateway

    Gọi API với header Authorization: Bearer <access_token>.

  6. Gateway kiểm tra JWT rồi chuyển xuống Service

    Kiểm tra chữ ký,iss,exp. Hợp lệ thì định tuyến và (thường) chuyển tiếp nguyên token.

5.3 Các khái niệm

  • Resource Server không giữ phiên (stateless): mỗi request tự mang token, Gateway không cần bộ nhớ phiên, scale ngang dễ. CSRF ít là vấn đề vì token nằm ở header do code JavaScript gắn vào, không phải cookie tự động gửi.
  • Nơi lưu token trong trình duyệt: in-memory (biến JavaScript, mất khi tải lại trang),sessionStorage, hoặc localStorage. Cả ba đều đọc được bởi JavaScript, nên đều lộ khi bị XSS. In-memory chỉ khó khai thác hơn một chút.
  • Refresh token trong trình duyệt: phần khó nhất. Nên dùng refresh token rotation(mỗi lần dùng đổi token mới, token cũ bị vô hiệu; dùng lại token cũ là báo động) và thời hạn ngắn.
  • CORS: SPA (origin :5173) gọi Gateway (origin :8080) và AS (origin :8180) là gọi chéo origin, nên cả hai phải bật CORS cho origin của SPA.
  • Thu hồi token: JWT còn hiệu lực đến khi hết hạn. Giảm rủi ro bằng access token ngắn hạn.
  • Defense in depth (phòng thủ nhiều lớp): Gateway kiểm tra JWT chưa đủ. Service phía sau cũng nên là Resource Server, kẻ nào gọi thẳng vào service (bỏ qua Gateway) vẫn bị chặn.
Nói thẳng với sinh viên

Cách A đúng chuẩn và rất phổ biến, đặc biệt khi dùng IdP bên thứ ba như Auth0 hoặc Keycloak. Điểm yếu cố hữu là token nằm trong JavaScript. Tài liệu hướng dẫn của IETF cho ứng dụng trình duyệt xếp BFF là kiến trúc được ưu tiên về bảo mật; SPA tự giữ token là lựa chọn chấp nhận được khi bạn chủ động chấp nhận rủi ro XSS.

6. BFF - Backend for Frontend (Gateway giữ phiên)

6.1 Ý tưởng

Chuyển toàn bộ phần OAuth từ trình duyệt sang Gateway. Gateway là confidential client: có client_secret, tự đổi code lấy token, giữ token trong bộ nhớ server (phiên). Trình duyệt chỉ nhận một cookie phiên và không bao giờ thấy token.

React SPAKhông có token Chỉ có cookie phiên HttpOnly.
hai chiều
Gateway (BFF)Confidential client Giữ phiên + token, chạy OAuth.
hai chiều
Auth ServerCấp token Cho Gateway.
đến
ServiceResource Server Nhận token do Gateway gắn.

6.2 Luồng đầy đủ

  1. Trình duyệt mở ứng dụng, chưa có phiên

    Gateway trả chuyển hướng (302) tới /oauth2/authorization/keycloak.

  2. Gateway đến Auth Server

    Gateway tạo state(và có thể cả PKCE), chuyển hướng người dùng tới /authorize.

  3. Auth Server đăng nhập người dùng, redirect về Gateway kèm code

    Địa chỉ nhận mặc định của Spring:/login/oauth2/code/{registrationId}.

  4. Gateway đến Auth Server(/token), back-channel

    Đổi code bằng client_id+client_secret. Lưu token vào phiên phía server.

  5. Gateway đến Trình duyệt

    Đặt cookie phiên (HttpOnly; Secure; SameSite), chuyển hướng về trang chính.

  6. SPA gọi /api/... kèm cookie đến Gateway đến Service

    Bộ lọc TokenRelay lấy access token từ phiên, gắn Authorization: Bearer ... rồi chuyển xuống service.

6.3 Các khái niệm

  • Cookie phiên và cờ bảo vệ:HttpOnly(JavaScript không đọc được, chặn XSS đọc phiên),Secure(chỉ gửi qua HTTPS),SameSite=Lax/Strict(hạn chế gửi cookie từ trang khác).
  • CSRF trở lại: vì cookie được trình duyệt tự gửi, cần chống CSRF (cookie XSRF-TOKEN + header X-XSRF-TOKEN) cho các request ghi dữ liệu (POST, PUT, DELETE).
  • Token Relay: Gateway chuyển token người dùng xuống service, để service biết "ai là người dùng thật".
  • Session store: chạy nhiều bản Gateway thì phiên phải dùng chung (Spring Session + Redis), nếu không người dùng sẽ bị đá ra khi request rơi vào bản khác. Gateway trở thành thành phần có trạng thái.
  • Cùng origin: SPA nên được phục vụ từ cùng origin với Gateway (hoặc sau cùng reverse proxy) để cookie hoạt động mượt và không cần CORS.
  • XSS vẫn nguy hiểm nhưng khác: kẻ tấn công không lấy được token để mang đi, nhưng vẫn có thể gọi API ngay trong trang nạn nhân khi trang còn mở. BFF thu hẹp thiệt hại chứ không xóa XSS.

        jwt.getClaimAsString("email"),
        jwt.getClaimAsString("preferred_username"),
        jwt.getSubject());

      }
    }
    return "unknown";
  }

@Configuration
class SecurityConfig {

  @Value("${app.oidc.client-id}")
  private String expectedAudience;

  @Bean
  SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
    http
      .authorizeHttpRequests(auth -> auth
        .requestMatchers("/actuator/health").permitAll()
        .anyRequest().authenticated())
      .oauth2ResourceServer(oauth2 -> oauth2
        .jwt(jwt -> jwt.decoder(jwtDecoder())));

    return http.build();
  }

  @Bean
  JwtDecoder jwtDecoder() {
    NimbusJwtDecoder decoder =
        NimbusJwtDecoder.withIssuerLocation("https://accounts.google.com").build();

    OAuth2TokenValidator<Jwt> withIssuer =
        JwtValidators.createDefaultWithIssuer("https://accounts.google.com");

    OAuth2TokenValidator<Jwt> withAudience =
        new JwtClaimValidator<List<String>>(
            "aud",
            audience -> audience != null && audience.contains(expectedAudience));

    decoder.setJwtValidator(
        new DelegatingOAuth2TokenValidator<>(withIssuer, withAudience));

    return decoder;
  }
}

Bước 6 : Bắt buộc PKCE với S256

Trong cấu hình nâng cao của client, tìm mục Proof Key for Code Exchange Code Challenge Method và chọn:

S256

PKCE bổ sung một cặp giá trị code_verifier và code_challenge vào Authorization Code Flow:

  1. SPA tạo ngẫu nhiên code_verifier.
  2. SPA tính code_challenge từ verifier bằng SHA-256.
  3. code_challenge được gửi trong request /authorize.
  4. Sau khi nhận authorization code, SPA gửi code_verifier tới /token.
  5. Keycloak kiểm tra verifier có khớp challenge ban đầu hay không trước khi cấp token.

Như vậy, nếu một bên khác chỉ lấy được authorization code nhưng không có verifier tương ứng, code đó không đủ để hoàn tất bước đổi token.

  3. Đăng nhập alice, trình duyệt quay về http://localhost:5173/?code=...&state=...

    Đây là front-channel, nơi code lộ ra (khớp bước 5).

  4. Tìm request POST .../token, xem tab Payload

    Thấy code_verifier=... được gửi lên (khớp bước 6). Hãy thử tính SHA-256 của nó trong phòng thí nghiệm ở mục 4.6, kết quả phải bằng code_challenge ở bước 2.

  5. Bấm Gọi /api/products

    Request tới Gateway có header Authorization: Bearer .... Thấy dữ liệu trả về, kèm tên alice(do Product Service đọc từ JWT).

  6. Thử không có token: 
    curl -i http://localhost:8080/api/products
# HTTP/1.1 401 Unauthorized
  7. Mở Application đến Session Storage

    Bạn thấy token nằm lù lù trong trình duyệt. Chép chuỗi access_token dán vào jwt.io để xem payload (chỉ làm với token demo). Đây là điểm yếu XSS của cách A.

Kết quả cần đạt

Sinh viên chỉ ra được: challenge đi trên URL, verifier chỉ đi ở /token, Gateway từ chối khi thiếu token, và token đọc được trong storage.

Bước 5. Cấu hình giao diện React trong src/App.jsx

Không dùng preferred_username làm claim bắt buộc khi chạy Google. Google thường cung cấp các claim như email,name và sub. Code dưới đây ưu tiên email, sau đó name và cuối cùng là subject.

import { useState } from "react";
import { useAuth } from "react-oidc-context";

export default function App() {
  const auth = useAuth();
  const [data, setData] = useState(null);

  if (auth.isLoading) return <p>Đang tải...</p>;
  if (auth.error) return <p>Lỗi: {auth.error.message}</p>;

  if (!auth.isAuthenticated) {
    return (
      <button onClick={() => auth.signinRedirect()}>
        Đăng nhập bằng Google
      </button>
    );
  }

  const profile = auth.user.profile;
  const displayName =
    profile.email ?? profile.name ?? profile.sub ?? "người dùng";

  const callApi = async () => {
    const res = await fetch("http://localhost:8080/api/products", {
      headers: {
        Authorization: `Bearer ${auth.user.id_token}`,
      },
    });

    const body = await res.json();
    setData(body);
  };

  const signOut = async () => {
    // Google không cung cấp RP-Initiated Logout theo cách Keycloak hỗ trợ.
    // removeUser() chỉ xóa phiên OIDC cục bộ của SPA.
    await auth.removeUser();
  };

  return (
    <div>
      <p>Xin chào {displayName}</p>
      <button onClick={callApi}>Gọi /api/products</button>
      <button onClick={signOut}>Đăng xuất khỏi ứng dụng</button>
      <pre>{JSON.stringify(data, null, 2)}</pre>
    </div>
  );
}

11.2 Gateway thành OAuth2 Client

Thêm dependency OAuth2 Client(thay cho Resource Server, hoặc dùng cả hai nếu cần nhận token trực tiếp từ client khác).

server:
  port: 8080
spring:
  security:
    oauth2:
      client:
        registration:
          keycloak:                      # registrationId, xuất hiện trong redirect URI
            client-id: bff-gateway
            client-secret: DÁN-SECRET-VÀO-ĐÂY
            scope: openid,profile
            authorization-grant-type: authorization_code
        provider:
          keycloak:
            issuer-uri: http://localhost:8180/realms/demo
  cloud:
    gateway:
      server:
        webflux:
          routes:
            - id: product
              uri: http://localhost:8081
              predicates:
                - Path=/api/products/**
              filters:
                - TokenRelay=              # lấy token từ phiên, gắn vào header Authorization
                - RemoveRequestHeader=Cookie  # không chuyển cookie phiên xuống service
@Configuration
@EnableWebFluxSecurity
class BffSecurityConfig {

  @Bean
  SecurityWebFilterChain chain(ServerHttpSecurity http) {
    return http
      .authorizeExchange(a -> a.anyExchange().authenticated())
      .oauth2Login(Customizer.withDefaults())     // chạy Authorization Code, giữ token trong phiên
      .csrf(c -> c.csrfTokenRepository(
          CookieServerCsrfTokenRepository.withHttpOnlyFalse()))
      .build();
  }
}
Hai điểm cần đối chiếu tài liệu

CSRF cho SPA: từ Spring Security 6 trở đi, cách cấu hình request handler và việc cookie XSRF-TOKEN được phát ra thay đổi (có nhiều bẫy với WebFlux). Xem mục "CSRF for Single Page Applications" trong reference docs của đúng phiên bản bạn dùng. Demo chỉ gọi GET nên chưa chạm tới vấn đề này.

PKCE cho confidential client: OAuth 2.1 khuyến nghị bật PKCE cả khi đã có secret. Spring Security có customizer sẵn cho việc này (OAuth2AuthorizationRequestCustomizers.withPkce()); hãy xác nhận cách gắn vào resolver trong docs phiên bản của bạn.

12. Lỗi thường gặp

Trình duyệt báo lỗi CORS khi gọi Gateway hoặc /token (cách A)

Origin của SPA (http://localhost:5173) phải được cho phép ở: (1) Keycloak, qua Web origins; (2) Gateway, qua cấu hình CORS trong Spring Security (preflight OPTIONS bị chặn trước khi tới route nếu chỉ cấu hình CORS trong Gateway mà không bật .cors() ở Security).

Invalid parameter: redirect_uri

URL SPA gửi không khớp với Valid redirect URIs đã đăng ký. Chú ý localhost khác 127.0.0.1, và cổng phải đúng.

Có token nhưng Gateway vẫn trả 401

Kiểm tra:issuer-uri phải giống hệt claim iss trong token (cùng localhost, cùng cổng). Token hết hạn (exp). Đồng hồ máy lệch quá xa. Gateway không truy cập được Keycloak để lấy JWKS.

invalid_grant hoặc PKCE verification failed ở /token

Verifier gửi lên không khớp challenge đã lưu: thường do tải lại trang giữa chừng làm mất verifier trong bộ nhớ, hoặc mở nhiều tab đăng nhập cùng lúc. Xóa storage và đăng nhập lại.

crypto.subtle is undefined

Web Crypto chỉ có trên "secure context" (HTTPS hoặc localhost). Nếu demo bằng địa chỉ IP qua HTTP thì thư viện OIDC không băm được.

Cách B: đăng nhập xong nhưng bị đẩy về trang login liên tục

Thường do cookie phiên không được lưu (domain/cổng khác nhau giữa lúc đăng nhập và lúc gọi), hoặc nhiều bản Gateway không dùng chung phiên.

Cách B: POST/PUT/DELETE bị 403

Thiếu header X-XSRF-TOKEN. Đây là CSRF hoạt động đúng; cần cấu hình phía SPA đọc cookie XSRF-TOKEN và gửi lại trong header.
